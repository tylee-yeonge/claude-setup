# 프로젝트 문서(docs/) 구조 규칙

계획·설계·조사 문서를 파일로 남길 때 따르는 표준. 이 문서의 골격만으로 자기완결적으로 작성한다 — 외부 예시 파일에 의존하지 않는다.

## 디렉터리 구조

문서는 해당 프로젝트 레포의 `docs/` 하위에 생성한다.

```
docs/
+-- research/                                    <- 조사/리서치 종합
|   +-- <topic>.md
+-- superpowers/
    +-- specs/                                   <- 설계 문서 (무엇을/왜)
    |   +-- YYYY-MM-DD-<topic>-design.md
    +-- plans/                                   <- 구현 계획 (어떻게, task 단위)
        +-- YYYY-MM-DD-<topic>.md
```

## 파일명 규칙

- topic slug는 영어 kebab-case (예: `user-auth`, `payment-api`, `cache-restructure`)
- spec과 plan은 **같은 topic slug**를 공유한다. spec에만 `-design` 접미어를 붙인다
  - spec: `2026-01-15-user-auth-design.md`
  - plan: `2026-01-16-user-auth.md`
- 대형 작업도 plan은 **단일 파일** — Phase별로 파일을 나누지 않고, plan 문서 안에서 `## Phase N` 섹션으로 분할한다
  - 예: `2026-01-16-user-auth.md` 하나가 Phase 0-6 전체를 담는다
- 날짜 접두어는 각 문서의 작성일 (spec과 plan의 날짜가 다를 수 있음)
- research 문서는 날짜 접두어 없이 `<topic>.md`, 작성일은 본문 메타에 기록

## 문서 유형과 역할

작업 흐름: research(필요 시) -> spec -> plan -> 구현

| 유형 | 위치 | 역할 | 수명 |
|---|---|---|---|
| research | `docs/research/` | 외부 사례/표준 조사 종합. 설계 판단의 근거 | 기록으로 잔존 |
| spec | `docs/superpowers/specs/` | 설계 결정과 근거. 사람이 읽고 판단하는 문서 | 설계 기록으로 잔존, 갱신 드묾 |
| plan | `docs/superpowers/plans/` | 실행 절차. 위에서 아래로 그대로 실행 가능 | 소모성, 체크박스가 계속 갱신됨 |

spec/plan 분리 원칙:

- **진행 로그(테스트 결과, 진행 상황 주석)는 plan에만 적는다.** spec을 진행 기록으로 오염시키지 않는다
- spec의 로드맵은 Phase 카탈로그(표) 수준까지만. Phase별 세부 체크박스/명령은 plan으로
- 설계 판단이 얇은 중간 규모 작업은 spec을 생략하고 plan 단독 작성 가능 — 이때 결정 근거는 plan의 §0 표에 직접 서술
- 설계 판단이 필요 없는 단순 작업(단발 버그 수정 등)은 문서 없이 대화 안에서 처리

## 언어

- 본문은 한국어. 코드 블록, 명령어, 식별자, 커밋 메시지는 영어
- `~/.claude/rules/markdown.md` 규칙(bold 인접 조사, Mermaid, 표 우선) 준수. 이모지 금지

## spec 골격

```markdown
# {{작업 제목}} 설계 ({{부제 또는 식별자}})

> 작성일: YYYY-MM-DD (최종 갱신: YYYY-MM-DD)
> 상태: Draft | Approved (설계)
> 대상: {{변경 대상 파일/모듈/시스템 (규모 수치 포함)}}
> 사유: {{한 줄 — 왜 이 작업이 필요한가}}
> 관련 분석: {{research/분석 문서 경로 (있을 때)}}
> Plan: {{plan 문서 경로}} (다 Phase 작업이면 "Phase 0-N 통합, §5 카탈로그 참조" 병기)

## 목차

- §0 배경과 확정된 결정
- §1 현재 구조 진단 (코드 사실 기반)
- §2-§N 설계 본문
- §5 로드맵 (Phase 카탈로그)
- §6 검증 기준
- §7 리스크와 한계
- §8 의사결정 로그
- 부록 A 관련 파일

## 0. 배경과 확정된 결정

### 0.1 동기
{{무엇이 왜 문제인가. 문제의 구조를 서술}}

### 0.2 확정된 결정
| # | 항목 | 결정 | 상세 |
|---|---|---|---|
| 1 | ... | **핵심 결정** — 부연 | §N, §8.N |

### 0.3 이 설계가 보장하지 않는 것
{{한계를 단정하지 않는 문장으로. "X를 자동으로 없애지 않는다" 등}}

## 1. 현재 구조 진단 (코드 사실 기반)
{{설계 주장의 근거가 되는 현재 코드의 사실. 라인 인용(path/to/file.py:123), 수치, 표}}

## 2.-N. 설계 본문
{{목표 아키텍처(Mermaid), 메커니즘, 매핑 표, 파일별 상세.
구현 계약 수준으로 정밀하게 — plan이 재해석 없이 옮겨 쓸 수 있어야 한다}}

## 5. 로드맵 (Phase 카탈로그)
{{공통 절차 요약 + 아래 표. 세부 체크박스는 두지 않는다}}
| Phase | 목적 | 핵심 산출물 | 선행 조건 | plan 섹션 |
|---|---|---|---|---|
| 0 | ... | ... | 없음 | 통합 plan §Phase 0 (진행 중) |
| 1 | ... | ... | Phase 0 | 통합 plan §Phase 1 (Draft) |

## 6. 검증 기준
{{시스템 전체의 통과 기준. 항목에 영역별 접두어 + 번호로 ID 부여
(예: F1.. 기능 동일성, E1.. 동등성, D1.. 장애/경계 시나리오).
체크는 plan의 Verification이 ID를 인용해 수행 — 이 문서는 기준의 원본으로만 유지}}

## 7. 리스크와 한계
{{항목별 굵은 제목 + 설명. 완화 방법이 있으면 § 참조}}

## 8. 의사결정 로그
### 8.N {{결정 항목}}: {{옵션 A vs 옵션 B}}
- **옵션 A (비채택)**: {{내용과 비채택 사유}}
- **옵션 B (채택)**: {{내용}}
- **사유**: {{왜 B인가}}

## 부록 A: 관련 파일
### A.1 수정 / A.2 폐기 / A.3 신규 / A.4 변경 없음 (의도적 보존)
{{"변경 없음"도 명시 — 누락이 아니라 의도적 보존임을 드러낸다}}
```

섹션 채택 가이드:

| 작업 성격 | 필수 | 생략 가능 |
|---|---|---|
| 아키텍처 전환 / 마이그레이션 | §0-§8 전부 + 부록 | 없음. 롤백이 복잡하면 §7에 롤백 전략 추가 (plan-template.md §7 형식 차용) |
| 신규 기능 (API/모듈 추가 등) | §0(0.2 결정 표 중심), 설계 본문, §6, 범위/범위 밖 | §1 진단, §5 카탈로그(단일 plan이면 헤더 링크로 대체), §8(결정이 자명하면) |
| 리팩토링 | §0, §1, 설계 본문, §6 | §5, §8 |

## plan 골격

```markdown
# {{작업 제목}} Implementation Plan

> 작성일: YYYY-MM-DD
> 대상: {{변경 대상 + 신규 생성물}}
> 사유: {{한 줄 — spec의 어느 문제를 실행하는가 (spec § 참조)}}
> Spec: `{{spec 파일명}}` ({{인용할 § 나열}})

> 체크박스(`- [ ]`)로 진행을 추적한다. 각 Task는 검증 Step과 커밋 Step으로 끝난다.

**Goal:** {{한 문단: 무엇을 만들고, 완료되면 무엇이 가능해지는가}}

**Architecture:** {{한 문단: 어떤 구조/원칙으로 (spec § 참조)}}

**Tech Stack:** {{사용 기술}}

**Note on verification:** {{자동 테스트만으로 안 닫히는 작업일 때 — 무엇이 완료 조건인지}}

## 0. 확정된 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | ... | ... | spec §N (spec 생략 시 근거를 직접 서술) |

## 0.1 이 계획이 보장하지 않는 것

- {{한계. spec §0.3에서 이 plan 범위에 해당하는 것 + plan 고유 한계}}

## Global Constraints

- {{모든 task 공통 제약. 판정 기준(회귀 정의), 범위 제한(하지 말 것), 다음 Phase로 미루는 것}}

---

### Task 1: {{task 제목}} (spec §N)

**Files:**
- Create/Modify/Move: `{{경로}}`

**Interfaces:** {{이 task가 생산하고 후속 task/Phase가 의존하는 이름들}}

- [ ] **Step 1: {{작업}}**

{{실행 가능한 명령/파일 내용/정확한 변경 서술 — placeholder/TBD 금지}}

- [ ] **Step N-1: 검증 — {{내용}}**

{{검증 명령과 기대 출력. 진행 로그(테스트 수치, 미완 사유)는 여기에 적는다}}

- [ ] **Step N: Commit**

{{git add/commit 명령 (Conventional Commits, 영어)}}

---

## Verification (after all tasks)

{{task 단위로 안 잡히는 통합 검증. spec §6의 기준 ID를 인용:
"- [ ] {{검증 내용}} — spec §6.1 F1의 선행 확인"}}

## Self-Review

**Spec coverage:** {{spec 각 § -> 어느 Task/Step 대응. 전수 확인}}
**Placeholder scan:** {{TBD/TODO 없음, 미완 항목은 체크박스로 추적 중임을 확인}}
**Type consistency:** {{task 간 생산/소비 이름·의미론 일치 확인}}
```

plan 작성 원칙:

- 각 Task는 검증 Step과 커밋 Step으로 끝난다 — task 단위로 검증 가능하고 커밋 가능해야 한다
- 검증을 먼저 쓸 수 있는 변경은 TDD 순서(실패하는 검증 작성 -> 실패 확인 -> 변경 -> 통과 확인)를 따른다. 파일 신규 작성처럼 선행 검증이 무의미하면 "작성 -> 검증 -> 커밋"으로 축약
- Step 본문에는 실행할 명령/내용을 그대로 넣는다. "적절히 수정" 같은 모호한 지시 금지
- 부분 완료 상태(제한된 환경의 테스트 결과 등)는 해당 검증 Step 아래 "진행 상황 (날짜):" 으로 기록하고, 잔여 확인은 Verification 항목으로 이관
- 다 Phase 작업은 plan 안에서 `## Phase N: {{제목}}` 섹션으로 분할한다. Task 번호는 Phase 충돌을 피해 `Task N-M` 형식, 각 Phase 끝에 해당 Phase의 검증 항목을 둔다
- 착수 전 Phase 섹션은 체크박스 항목 수준의 **Draft**로 두고 상태를 명시한다 — 착수 시 진행 중 Phase 수준(Files/Interfaces/Step/검증/커밋)으로 세부화한다

## research 골격

```markdown
# {{Topic}} — {{부제}}

> {{한 줄 목적: 무엇을 조사했고 이 레포의 어떤 판단에 쓰이는지}}
> 작성일: YYYY-MM-DD

## TL;DR

## {{본문 섹션들}}
```

## plan-template.md와의 관계

- 문서의 위치/파일명/유형 분리는 이 규칙이 우선한다
- `~/.claude/rules/plan-template.md`의 § 골격은 위 spec 골격의 원형이다. spec에 없는 섹션(§7 롤백 전략의 옵션 비교 표 등)이 필요하면 거기서 차용한다

## 기타

- 프로젝트 레포가 아닌 개인 메모 성격의 문서는 `~/.claude/plans/`에 같은 파일명 규칙으로 저장 가능
