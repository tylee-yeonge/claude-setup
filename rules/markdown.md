# Markdown 작성 규칙

## 현재 상태 기준 작성 (스냅샷 원칙, diff 금지)

모든 마크다운 문서(plan.md, README, 설계 문서, 가이드 등)는 **수정을 마친 시점의 스냅샷**으로 쓴다. 어떻게 여기까지 왔는지가 아니라 지금 무엇인지만 담는다.

**판정 질문**: "이 문서를 처음 읽는 사람에게 이 문장이 필요한가?" 이전 상태를 알아야만 뜻이 통하는 문장이면 지운다. 변경 추적은 git diff / 커밋 이력이 담당하므로 마크다운을 변경 로그로 만들지 않는다.

### 금지 패턴

문서를 갱신할 때 실제로 자주 새어 들어오는 형태다. 왼쪽을 쓰지 말고 오른쪽으로 쓴다.

| 금지 | 대신 |
|---|---|
| "원안은 A 였으나 지금은 B", "기존 A → B" | "B" 만 |
| "A 에서 B 로 변경/교체/갱신했다" | "B" 만 |
| 옛 내용을 남긴 채 붙이는 "대체됨 / 폐기됨 / 무효 / 재설계 대기" 표시 | 옛 내용을 **삭제** |
| "이전 판에서는", "직전 버전 대비", "기존에는" | 삭제 |
| 제목·셀 옆의 "(YYYY-MM-DD 갱신)", "(수정됨)", "(정정)" | 삭제 |
| "추가했다 / 제거했다 / 정정했다" | 결과 상태만 서술 |
| 취소선(`~~`)으로 남긴 옛 항목·행 | 삭제 |
| "위 표를 다음으로 교체한다" 식 before/after 병기 | 최종 내용만 |

### 갱신 방법

- 해당 문단·표·행을 새 내용으로 **덮어쓴다.** 옆에 병기하거나 아래에 주석으로 달지 않는다.
- 옛 값이 판단 근거로 필요하면 **변경 서술이 아니라 현재 근거 문장**으로 녹인다.
  - 나쁨: "A 로 정했다가 B 로 바꿨다"
  - 좋음: "B 를 쓴다. A 는 리드타임이 일정에 맞지 않아 비채택"
- 날짜는 "언제 바꿨나"가 아니라 **"언제 확정된 사실인가"**로만 적는다. 확정일이 독자의 판단에 쓰이지 않으면 날짜도 생략한다.

### 예외 (좁게 — 확대 해석 금지)

1. **CHANGELOG / 릴리스 노트** — 변경 이력 자체가 문서의 목적.
2. **의사결정 로그의 비채택 옵션** (`plan-template.md` §8) — 변경 이력이 아니라 현재 결정의 근거다. 단 비채택 사유만 적고 "원래는 이걸 채택했었다"는 쓰지 않는다.
3. **plan 의 진행 로그** (`docs-structure.md`) — 체크박스 진행 추적용. 여기서도 스냅샷으로 쓴다: "무엇을 언제 바꿨다"가 아니라 **"지금 어디까지 됐고 무엇이 남았다"**.

이 셋 밖에서는 예외를 만들지 않는다. 특히 **"독자가 혼동할 수 있으니 대체 표시를 남긴다"는 예외가 아니다** — 혼동의 원인은 옛 내용이 문서에 남아 있는 것이므로, 표시를 붙이는 게 아니라 지우는 것이 해법이다.

## Bold/Italic 인접 한글 렌더링 문제

CommonMark 스펙상 닫는 `**`/`*`는 **right-flanking delimiter run**일 때만 emphasis로 인식된다. 다음 조건을 모두 만족해야 한다:

1. 앞이 공백이 아닐 것
2. (a) 앞이 구두점이 아니거나, (b) 앞이 구두점이면 뒤가 공백/구두점일 것

한글(Hangul syllable)은 Unicode 카테고리상 letter(Lo)라 구두점도 공백도 아니다. 따라서 **닫는 `**`/`*` 바로 앞이 구두점(`)`, `.`, `!`, `?`, `,`, `]` 등)이고 뒤가 한글이면 emphasis가 풀려 asterisk가 그대로 노출된다.**

VS Code 미리보기(markdown-it), GitHub, GitLab 모두 CommonMark를 따르므로 동일 증상이 나타난다.

### 깨지는 패턴 예시

| 입력 | 의도 | 실제 렌더링 |
|------|------|-------------|
| `**용어(영문명)**를` | **용어(영문명)** 를 | `**용어(영문명)**를` (raw) |
| `**Quantization)**는` | **Quantization)** 는 | `**Quantization)**는` (raw) |

### 권장 수정: 구두점을 bold 밖으로

핵심 용어만 굵게 처리하고, 부가 정보(영문 풀네임, 약자 등)는 일반 텍스트로 둔다. 한글 조사는 영문/숫자/letter에 붙으면 정상 동작한다.

- `**IoU(Intersection over Union)**를` → `**IoU**(Intersection over Union)를`
- `**양자화(Quantization)**는` → `**양자화**(Quantization)는`
- `**엔진(.trt 파일)**을` → `**엔진**(.trt 파일)을`

여러 용어를 한 번에 굵게 한 경우는 분리:
- `**A(X)와 B(Y)**를` → `**A**(X)와 **B**(Y)를`

이 규칙은 italic(`*...*`)에도 동일하게 적용된다.

### 정상 동작하는 패턴 (수정 불필요)

닫는 `**` 앞이 letter(한글/영문/숫자)면 right-flanking 조건이 성립한다.

- `**도구**를` (한글 letter + 한글)
- `**FP**다` (영문 letter + 한글)
- `**YOLO11**이다` (숫자 + 한글)
- `**Backbone(백본)**:` (구두점 + 구두점 → 2b 조건 성립)

## 숫자/날짜 범위

`~` 대신 `-` 사용. `~`는 마크다운 일부 렌더러(특히 GFM 확장)에서 취소선(`~~text~~`)으로 오인식될 수 있다.

- 잘못: `2018~2024`, `100~200ms`
- 옳음: `2018-2024`, `100-200ms`

## 다이어그램

ASCII 아트 대신 Mermaid 사용. GitHub/GitLab 모두 기본 지원한다.

### Mermaid 노드 라벨이 박스 밖으로 잘리는 문제 (한글)

mermaid는 노드 박스 폭을 "텍스트 실제 폭"을 측정해 결정한다. 한글은 폰트 폴백 시 글리프 폭이 측정값과 어긋나기 때문에(위 "CJK 문자 너비"와 같은 뿌리), **mermaid가 계산한 박스 폭보다 실제 텍스트가 넓어 글자가 박스 경계 밖에서 잘린다.** 한 줄이 길수록 폭 오차의 절대값이 커져 더 심하게 잘린다.

`config: { flowchart: { htmlLabels: true } }` front matter로 완화할 수 있지만 **GitHub은 securityLevel이 strict로 고정되어 HTML 라벨이 비활성화(SVG text 모드 강제)되므로 이 옵션이 무시된다.** 즉 config 옵션에 의존하면 GitHub에서 그대로 잘린다.

**핵심 규칙: VS Code 미리보기와 GitHub 양쪽을 모두 고려하면, 노드 라벨의 긴 한 줄을 `<br/>`로 짧게 쪼개는 것이 유일하게 두 환경에서 통하는 해법이다.** `A / B / C`처럼 슬래시로 한 줄에 나열하지 말고 각 항목을 `<br/>`로 분리한다. 엣지 라벨(`-->|"..."|`)도 동일하게 적용.

```
# 잘림 (한 줄이 길다)
C["학습 설정<br/>data.yaml 작성 / 모델 크기 선택 / Hyperparameter 설정"]

# 정상 (항목별 줄바꿈으로 한 줄 길이를 줄임)
C["학습 설정<br/>data.yaml 작성<br/>모델 크기 선택<br/>Hyperparameter 설정"]
```

한계: 줄 분할은 폭 오차의 절대값을 줄여 클리핑을 사라지게 하는 것이지 측정 오차 자체를 없애지는 못한다. 따라서 한 줄은 가능한 한 짧게 유지한다.

## CJK 문자 너비와 ASCII 박스

한글은 "이상적인" 모노스페이스 폰트에서 2칸을 차지하지만, **실제 렌더링 폭은 폰트에 좌우된다.** VS Code 마크다운 미리보기의 코드블록 폰트에 한글 글리프가 없으면 시스템 폴백 폰트로 한글을 그리는데, 이때 한글 폭이 하이픈/공백의 정확히 2배가 아니라 어긋난다. 즉 **소스 텍스트에서 폭을 2배로 맞춰도(하이픈 11개 = 한글 글자 폭 합) 미리보기에서 깨질 수 있다.** ASCII 박스 정렬은 한글이 섞이는 순간 신뢰할 수 없다.

**핵심 규칙: 정렬이 필요한 위치(박스 셀, 표 칸)에 한글이 들어가면 ASCII 박스를 쓰지 말고 마크다운 표(`| ... |`)를 쓴다.** 표는 렌더러가 실제 글리프 폭을 측정해 셀 폭을 자동 조정하므로 폰트와 무관하게 정렬된다. 2x2 mosaic 같은 공간 배치도 2x2 표로 표현 가능하다 - "표로는 표현 불가"가 아니다.

### 변환 대상 식별 기준

다음 패턴이 동시에 보이면 마크다운 표로 변환한다:

1. `+----+`/`+====+` 같은 **가로 구분선**과 `| ... |` **세로 셀**이 함께 쓰임 (= 표 형태로 자료를 정리하려는 의도)
2. 셀 내용에 **한글 문자열** 포함 (정렬이 깨지는 원인)
3. 행/열이 **데이터 비교/속성-값** 구조 (단순 시각화가 아님)

위 셋을 모두 만족하면 ASCII 박스가 깨져 있을 확률이 높고, 마크다운 표가 더 적합하다.

### 변환 예외 (ASCII 유지 또는 다른 도구 사용)

- **디렉터리/파일 트리**: `+-- src/`, `+-- README.md` 같은 트리 표기. 시각적 계층이 핵심이라 표보다 ASCII가 적합. **단, 정렬되는 부분(`+--` 접두사)은 순수 ASCII여야 하고, 한글은 정렬과 무관한 trailing 주석(`<- 설명`)으로만 둔다.** 한글이 트리의 정렬 위치에 들어가면 안 된다.
- **도형/위치 시각화**: BBox 겹침 그림처럼 **공간적 배치 자체**를 보여주고 셀 안에 한글이 없는 경우만 ASCII로 유지한다. 셀 안에 한글 라벨이 들어가면(예: 4분할 mosaic의 "이미지1") ASCII 박스는 정렬이 깨지므로 **마크다운 표로 변환**하거나, 굳이 ASCII가 필요하면 한글 대신 짧은 ASCII 라벨(`img1` 등)을 쓴다.
- **흐름도/관계도**: 노드와 화살표 다이어그램은 Mermaid로 변환 (위 "다이어그램" 항목 참고).
- **코드 블록 내부 출력 문자열**: Python `print("...")` 안에 들어가는 ASCII 표는 코드의 실행 결과 일부라 유지.

### 변환 전/후 예시

**변환 전** (한글이 섞여 정렬이 깨지는 ASCII 박스):

````markdown
```
+----------+----------+----------+----------+
| 정밀도   | 모델 크기| 추론 속도| mAP      |
+----------+----------+----------+----------+
| FP32     | 25 MB    | 15 FPS   | 0.45     |
| FP16     | 12 MB    | 30 FPS   | 0.44     |
| INT8     | 6 MB     | 55 FPS   | 0.42     |
+----------+----------+----------+----------+
```
````

**변환 후** (마크다운 표):

```markdown
| 정밀도 | 모델 크기 | 추론 속도 | mAP  |
|--------|----------|----------|------|
| FP32   | 25 MB    | 15 FPS   | 0.45 |
| FP16   | 12 MB    | 30 FPS   | 0.44 |
| INT8   | 6 MB     | 55 FPS   | 0.42 |
```

### 표가 어울리지 않는 박스 (= 항목 나열 박스)

같은 ASCII 박스라도 "행/열 비교 표"가 아니라 단순히 **항목을 묶어 강조하는 박스**라면, 마크다운 표보다 **소제목 + 리스트**가 자연스럽다.

**변환 전**:

````markdown
```
+-----------------------------------------+
| TensorRT 최적화                          |
|                                         |
| Layer Fusion (레이어 합치기)            |
|   Conv + BN + ReLU -> FusedCBR          |
|                                         |
| Kernel Auto-Tuning                      |
|   수백 개 커널 중 최적 선택              |
+-----------------------------------------+
```
````

**변환 후**:

```markdown
**TensorRT 최적화**

- Layer Fusion (레이어 합치기): `Conv + BN + ReLU` -> `FusedCBR`
- Kernel Auto-Tuning: 수백 개 커널 중 최적 선택
```

### 작성 시 점검 순서

새 콘텐츠를 쓸 때 또는 기존 파일을 리뷰할 때 다음 순서로 판단한다:

1. 행/열 데이터 비교인가? -> **마크다운 표**
2. 항목 강조 박스인가? -> **소제목 + 리스트**
3. 노드/화살표 흐름인가? -> **Mermaid**
4. 디렉터리 트리/도형 시각화/공간 배치인가? -> **ASCII 유지**
5. 코드 출력 문자열인가? -> **그대로 유지** (코드 동작의 일부)
